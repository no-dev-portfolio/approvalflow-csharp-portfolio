# 運用・展開の検討

## ローカルデモ

Composeは127.0.0.1へ限定しDevelopmentで実行。EnsureCreatedで初期テーブルとデモユーザーを作成。SQL Server Developer Editionは開発・試験専用。SA接続とTrustServerCertificateもローカル専用の簡略設定。初回構築後にモデルを変更する運用を想定したマイグレーション履歴は未整備。

## 本番へ進める際の作業

Productionではデモ初期化を実行しない。database/schema.sqlは初期スキーマの参照用で、新規の専用DBに管理者が適用する。既存DBを更新する場合はEF Migrationsとレビュー済みの移行・ロールバック・バックアップ手順を追加する。

独自アカウントの運用管理画面は未実装。Entra ID等のOIDCによる認証を導入し、ロールの割当と退職者のアクセス失効を設計する。現在のCookieは30分固定期限。ログアウトは当該ブラウザーのCookie削除で、漏えい済みCookieをサーバー側で即時失効するセッション台帳は未実装。

HTTPS、正式証明書、専用DBユーザーの最小権限、シークレット管理、Data Protection鍵の永続化・共有、監視、バックアップと復旧試験を設定する。複数プロセスのログイン回数制限は現状のメモリ内IP制限では共有されない。リバースプロキシからの転送ヘッダーは信頼するプロキシだけを明示して扱う。

## Azureを選ぶ場合（設計検討のみ）

コンテナ化したアプリをApp Service / Container Appsへ、データをAzure SQLへ配置する案を検討できる。実際の展開は未実施。リソースの課金が発生するため、この成果物を作る過程では作成していない。

1. 検証用サブスクリプションと予算上限、リージョン、ネットワークを確定。
2. Azure SQLの互換性・接続・制約・トランザクションを同じ統合試験で確認。
3. アプリの接続資格情報をKey VaultまたはマネージドIDに移す。SAアカウントを使わない。
4. Production、HTTPS、認証基盤、鍵永続化、スケールアウト時の制御を整備。
5. 本番相当の負荷・障害・復旧試験とログの個人情報確認を実施。
6. デプロイ前後のヘルスチェック、監視通知、ロールバックを確認。

Azure Functions / Blob / Queue / Isolated Worker / Azure Pipelinesはこの作品では実装していない。それらが必須の案件には追加の実装・検証が必要。

## v1.0.1の補足

認証CookieとAntiforgery CookieはProductionでSecureを常時指定する。TLS終端時はアプリがHTTPSを認識できるよう、信頼する転送元だけを設定する。

ログイン制限は成功・失敗を合わせたIP単位の固定窓10回/分で、メモリ内に保持する。アカウント単位の制限はない。複数IPからの試行、窓の境界付近の集中、プロキシ共有IPの影響には別の対策が必要。アカウント単位のロック・分散カウンター・MFA等は本作に未実装。

Auditsの申請への外部キーは連鎖削除である。アプリは申請削除APIを提供しないが、DB管理操作で申請を削除すると履歴も削除される。耐改ざん保管を必要とする運用では別の監査保管を設計する。

試験DBの削除は正常な終了処理で実施し、検証スクリプトはその実行IDの残存数をSQLで確認する。強制停止・プロセス異常終了時の削除は保証しない。接続先と名前を確認したうえで、残存する試験専用DBを管理者が処理する。
