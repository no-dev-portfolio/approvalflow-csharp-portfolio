## 指摘事項

### CR-01（P2）履歴・一覧の時刻が9時間ずれて表示される

- 対象: `src/ApprovalFlow/Program.cs:93,100`、`src/ApprovalFlow/wwwroot/app.js:6`、`Models.cs:22,33`
- 内容: `Audit.At`・`Request.CreatedAt`は`DateTime.UtcNow`で保存される。DBのdatetime2から読み戻すと`Kind`が`Unspecified`になり、JSONには`Z`もオフセットも付かない。ブラウザーはオフセットなしの日時をローカル時刻として解釈するため、UTCの値がそのままJSTの時刻として表示される。
- 根拠: `docs/screenshots/approved.png`の履歴は「2026/10/28 3:19:06」「3:19:15」「3:21:02」。一方、`integration.trx`の開始は同日03:33（UTC）で、作者の作業はJSTの日中である。スクリーンショットの時刻はUTCの値と見るのが自然で、JSTの実時刻（12:19頃）より9時間早い。
- 期待: 日本のブラウザーでは実際の操作時刻（JST）が表示される。
- 影響: 承認履歴は本作品の中心機能で、画面上の操作時刻が誤る。一覧の作成日も、UTCの15時以降はJSTで日付が1日ずれる。試験は時刻をまったく検証していない。
- 改善案: JSON出力でUTCと分かる形式（`Z`付き）にそろえる。たとえばEFの値変換で`DateTimeKind.Utc`を付与する。あわせて表示値を検証する試験を追加する。
- 確度: コード読解とスクリーンショットによる判断。アプリは実行していない。

### CR-02（P3）整形検査の成功を示す生ログがない

`VALIDATION.md`は「ソース・試験プロジェクトの整形検査 両方成功」の証拠に`evidence/verification.log`を挙げている。しかしこのログは11行で、復元・ビルド・テストの出力だけであり、`dotnet format`の出力はない。`summary.json`にも「Both source and test projects verified」という文字列があるだけで、実行記録ではない。

### CR-03（P3）「残存0件を確認」の根拠がない

試験DBの削除後の残存確認は、証拠欄に「Factory.DisposeとSQL確認」とあるが、SQLの実行記録は同梱されていない。`Factory.Dispose`は`EnsureDeleted`を呼ぶ実装だが、試験が異常終了した場合はDBが残る。

### CR-04（P3）証跡の来歴が不明確

`integration.trx`は1ファイルのみ。`verification.log`（2秒）と`compose-test.log`（3秒）の2回の実行は同じパスの結果ファイルを上書きしており、同梱のtrxは実行時間から見て後者と対応する。`rate-limit.json`にも実行時刻がない。

### CR-05（P3）「ロール拒否403」は一部にのみ当てはまる

VALIDATION.mdは「ロール拒否403を確認」としている。コードでは、作成・編集のロール違反が403である一方、状態遷移（承認・差戻し・申請）のロール違反は409「権限または状態が変更されました」を返す。DESIGN.mdには409と書かれているが、VALIDATION.mdの表現は広すぎる。試験が403を確認しているのは「承認者による新規作成」のみで、承認者による編集や、申請者による承認の403/409の区別は検証していない。

### CR-06（P3）原子性の試験は編集経路のみ

`AuditFailureRollsBackRequestUpdate`は、トリガーで「Edited」の履歴挿入だけを失敗させる。状態遷移（`Transition`）と新規作成の原子性は試験されていない。コード上はどちらも同一トランザクションで、読解した範囲では正しい。

### CR-07（P3）セッション失効後のログインが400になる可能性

- 対象: `app.js:9,10`（`api()`の401処理）、`Program.cs:30`
- 内容: CSRFトークンはログイン中のユーザーに結び付く。30分でCookieが失効すると`api()`は401でログイン画面を出すが、トークンを取り直さない。失効前のトークンのままログインを送ると、Antiforgeryの検証で400「画面を再読み込みして操作してください」になる、と読める。再読み込みで回復する。
- 確度: ASP.NET Coreの仕様とコード読解による推測。未実行。

### CR-08（P3）開発モードでの入力異常の扱いが未検証

Composeのアプリは`Development`で動く。minimal APIは開発環境で不正リクエストを例外として投げる設定が既定のため、不正なJSONや型違い（金額に小数など）が400ではなく独自の500応答になる可能性がある。試験は`Testing`環境で実行され、不正JSON・Content-Type欠落・Version欠落の試験もない。未実行の推測である。

### CR-09（P3）ログイン制限の性質

固定窓・IPごと・メモリ内で、成功したログインも数える。分散したIPからのパスワード試行や、窓の境界をまたぐ短時間の試行は制限されない。プロキシの共有IPの問題とメモリ内の制約はOPERATIONS.mdに記載があるが、アカウント単位の制限がないことは書かれていない。

### CR-10（P3）そのほかの軽微な点

- 履歴は申請の削除時に連鎖削除される（`schema.sql`の`ON DELETE CASCADE`）。削除機能はないが、耐改ざん保管は未実装と明記されており、設計上の注記にとどまる。
- Antiforgeryのクッキーは`Secure`が常時ではない（認証クッキーは本番で常時Secure）。TLSを終端するプロキシの背後での設定の不整合になりうる。
- `LogoutInvalidatesClientSession`は、クライアント側のCookie削除しか検証しない。OPERATIONS.mdにサーバー側の即時失効が未実装と明記されているため、試験名が過大な表現である。
- CIの`actions/checkout@v7`などのバージョンは、CIを未実行のため実在を確認していない。
